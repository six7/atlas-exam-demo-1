Atlas · Prototype environment

Every prototype, from every branch, in one place

Build in your own folder, push, and it shows up for the whole team — with a screenshot and somewhere to leave comments. Here is the whole workflow.

The one thing to understand

You edit registry.json. CI fills Supabase. The hub reads Supabase.

Nothing else is asked of you — and nothing should write to Supabase by hand, from a prototype, or from a script.

01

Create it on your machine

Open the hub and click New prototype. Describe what you are building, pick your agent — Claude Code, GitHub Copilot, or Codex — and it hands you a link, clone commands, and a prompt.

The hub does not create anything itself. The prompt names the exact folder and the exact registry.json entry, and your agent writes them in your checkout. That is the only place it can work: creating a prototype means writing into git.

Heads up

The deep links differ in what they actually do. Claude Code fills the prompt in a clone you already have — it does not clone. Copilot opens the Copilot app on this repo with the prompt. Codex has no deep link. Clone commands are always offered, and always work.

Or by hand

Create src/prototypes/my-feature/index.tsx with a single default export, then add an entry to src/prototypes/registry.json: 

{
  "id": "my-feature",
  "name": "My Feature",
  "author": "Your Name",
  "description": "What you're exploring.",
  "createdAt": "2026-08-24"
}

The id is the URL — this one lives at /prototypes/my-feature. Then check it: 

npm run validate:registry

All five fields are required, the id must match the folder name, and the same check runs on your pull request. A half-filled entry becomes a card on the hub that nobody owns, so it fails here instead.

02

Share it

Push the branch and open a pull request. That is the whole step.

git checkout -b my-feature
git add .
git commit -m "Add my feature prototype"
git push -u origin my-feature

Then wait. Registration runs after Vercel finishes deploying — not when you push — because the screenshot needs a live URL. In practice, a minute or two after the deploy goes green.

When it lands, your prototype is on the hub for everyone: screenshot, your name, your branch, the PR number, and a link that opens it on your branch's deployment rather than someone else's.

You do not run a command, and you do not touch Supabase.

03

Read and leave comments

Open a prototype and press C. Hovering outlines elements; clicking one attaches your comment to it. The comment then shows as an avatar pin sitting on that element, so the next person sees exactly what you meant.

The Feedback button, bottom right, does the same thing and also opens the thread. Use it without picking an element when the comment is about the page as a whole.

  • The first time, it asks what to call you. Stored in your browser only; you will not be asked again.
  • On the hub, every card shows its comment count and the element each comment points at — so you can review everything without opening a single prototype.
  • Comments stay with the branch they were left on, so feedback on your work does not leak onto someone else’s.
Anchors move

Pins are attached by finding the element again in the page, so restructuring your prototype can detach one. The comment is never lost — it stays in the panel marked (gone) with a note of what it pointed at. To make a pin survive edits, give the element a stable handle: data-feedback-id="activity-feed".

You never add the overlay to your prototype. It loads from the main deployment, which also means improvements to commenting reach old prototypes without anyone rebuilding them.

04

When the PR closes

Merged or closed, the prototype moves into Merged & closed at the bottom of the hub.

Nothing is deleted. The comments stay attached, so you can go back months later and read what people actually said about it.

Removing a prototype

Delete its entry from registry.json, delete its folder, and push. The row disappears from the hub on the next deploy — you do not need to clean anything up by hand.

House rules

  • Your folder is yours. Don't edit anyone else's src/prototypes/<their-id>/.
  • Never write to Supabase. Not from a prototype, not from a script, not by hand. CI owns that table. If a prototype seems to need a write, it doesn't — ask first.
  • Use tokens, never hex. var(--color-text-primary), not #162F02. Dark mode then works for free.
  • Shared components are for using, not editing. Need a different Button? Build your variant inside your own folder.
  • Don’t add the feedback overlay yourself. Every prototype gets it automatically, from the main deployment. That is how old prototypes keep getting improvements.

When something looks wrong

What you seeWhat it means
Your prototype isn't on the hub The deploy hasn't finished, or registration is still running. Check the Actions tab on the PR.
Card says “No screenshot yet” The screenshot failed. Open your prototype's URL directly — if it errors there, fix that first and push again.
Feedback says “not in the shared registry yet” Push and let a deploy finish. Comments attach to a registered prototype, so there is nothing to attach to yet.
Hub shows a “Local registry” notice Supabase isn't configured, so you're seeing only this branch. Expected on your machine; wrong on a deployment.
A pin vanished after you edited the prototype The element it pointed at moved. The comment is still there, marked (gone). Add data-feedback-id to keep a pin across edits.
Your pull request fails on “Check registry.json” Run npm run validate:registry — it names the exact field or folder that is wrong.
Your name is wrong on comments Clear atlas.feedback.display-name from localStorage. It will ask again next time.

Working offline from the shared hub

Without Supabase configured, everything still runs. The hub falls back to your branch's registry.json and says so on screen. Build and review your own prototype exactly as normal — it reaches the shared hub when you push.

Deeper detail lives in AGENTS.md and CLAUDE.md at the repo root. Brand and token reference is in DESIGN.md.
